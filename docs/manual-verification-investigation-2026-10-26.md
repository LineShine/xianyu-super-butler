## 已完成的修正

1. 验证资源策略补齐官方列出的精确资源主机；记录资源失败、页面错误码和滑块提交业务状态。
2. 本机改为原生身份的可见浏览器，用户直接操作；不再通过截图转发本机鼠标事件。
3. 本机验证入口改为官网消息页。只观察官网自身的 Token 响应，不注入 SDK 调用、不重放旧验证链接、不通过独立 HTTP 客户端轮询；保存成功 Token 时沿用官网实际设备 ID。
4. 同步和异步 Token 客户端统一 JSON/签名构造，删除预先编码的参数、固定安全参数占位值和历史页面追踪值。官方 SDK 离线对照确认存在这些差异，但真实复测没有证明它们是滑块失败的充分原因。
5. 响应仅在内存中短暂保存；关闭后取消在途解析。账号归属、Cookie 和队列期限校验保留，只有真实 Token 成功才启用账号。诊断不读取官网消息列表内容。

## 尚不能确定的部分

现有证据指向新建验证会话与平时 Chrome 已有会话的差异，不能进一步确定是平台对会话、客户端环境还是其他风险因素的判断；也不能据此认定账号封禁、IP 被封或用户拖动不正确。

阿里云公开文档没有给 `error:xxxxx` 字母数字码提供原因映射，要求通过官方支持排查。因此不能把 `tizPTs` 或 `code=300` 直接翻译成某个确定根因。
